## Current UI controls to use

The source is concentrated in [EscrowDashboard.tsx](../apps/web/components/EscrowDashboard.tsx), [action-policy.ts](../apps/web/lib/client/action-policy.ts), [chain.ts](../apps/web/lib/chain.ts) and [server/routes.ts](../apps/web/lib/server/routes.ts).

- **Wallet/session:** local Client/Freelancer/Treasury/six-Arbiter selector, browser-wallet connect, local-chain switch, SIWE sign-in/sign-out, and a session-expiry display. Treasury selector is local-demo only per A-59.
- **Navigation:** enter one agreement ID; there is intentionally no public job directory. The milestone ledger selects one milestone at a time.
- **Create:** the Client can open “Create a private agreement,” enter the named freelancer, token, review window, revision limit, private title/description/scope/rules, and 1–10 milestones with raw-unit amounts, duration and acceptance criteria. “Review and create proposal” leads to a final confirmation modal before the wallet prompt.
- **Job actions:** Accept proposal; Cancel expired proposal; Fund with exact allowance; Cancel unfunded agreement; Submit deliverable; Approve; Reject and save privately; Resubmit; Release after review window; Refund missed milestone; Refund after no revision; Open dispute; Match deposit; Withdraw.
- **Dispute actions:** private evidence text plus optional attachment; Advance phase; sealed vote; reveal vote. The current panel, phase/round, deadlines, deposit amount and evidence list are rendered.
- **Local controls:** visible only for a local demo role: advance chain time (1–86,400 seconds), set manual/reject/synchronous randomness mode, and fulfill a request by ID.
- **Read surfaces:** private terms/criteria, private rejection reasons, authorized files/evidence, per-job/per-milestone state, balances, chain events and append-only private audit entries with source labels.

## UI/source execution findings and remaining gaps

1. **Private seed data is absent.** Chain seeds have commitments but no matching private API records for terms, rejection reasons or evidence. Use UI-created agreements to prove private-content behavior; seeded job pages alone cannot close P-03/P-04.
2. **Both arbitration fallback paths have separate browser proof.** Job35 covers randomness retry exhaustion. Job37 covered a Panel1 with three commits and no reveals followed by a fresh Panel2 with no commits or reveals; round 2 settled at 5,000 bps with the human-readable reason “Panel 2 did not reach quorum,” and the ledger reconciled the posted deposit refund. The normal 6,000-bps Panel2 ruling remains separate evidence.
3. **Settled dispute UI is integrated; access/audit edges remain.** `DisputePanel` renders outside the funded-only action block, and the final summary is assembled from matching `MilestoneResolved` and `DisputeSettlementCredited` events. The job29 compiled screenshot confirms the normal Panel2 result and amounts; the final Treasury screenshot confirms the “Treasury forfeiture” source-2 label. Settled dispute17's evidence owner signed in and read both private text entries. Unassigned/other-party denial and arbiter-read audit checks remain.
4. **F-45 registry UI is scoped PASS; arbitrary outsider role remains absent.** The compiled local UI shows the pinned on-chain owner and complete current roster to every role; the owner can add and remove wallet addresses through the confirmation and receipt flow, while a non-owner can only read. A no-job-loaded 6→7→6 cycle succeeded, returned to the original six members, and left all 32 recorded panels unchanged. Demo wallets are synthetic; off-chain identity vetting is still required for real arbiters and no private identity details are collected. Over-cap, zero/duplicate, and helper-level at-cap refusal checks exist, but a populated 128-member browser/chain case and corrupt-state UI run remain untested. Use Treasury and an unassigned arbiter for available denial checks; route-level stranger/404 tests remain separate evidence.

6. **New-job private cache isolation passed.** Fresh job36 was created with two milestones (1 and 2 raw USDC); after switching from job32 with three files, the post-fetch view showed job36's private title and no old Download/evidence. The source clears the private view and advances its read generation before publishing the new job, and stale asynchronous private reads cannot commit into a newer job/session context.
