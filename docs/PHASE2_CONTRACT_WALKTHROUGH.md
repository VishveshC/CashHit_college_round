# Phase 2 function walkthrough

This describes the agreed Phase 2 contract slice. Actual verification status and limitations belong in PHASE2_REPORT.md; no wallet UI or arbitration is implied. Parties, hashes, opaque references and timestamps are public; private files/text/salts stay off-chain and their secure backend remains Phase 4.

- **submitMilestone:** The named freelancer records a nonzero deliverable hash while a funded milestone is Ready and before graceEnd. The contract appends version 1 and starts the agreed review clock; an optional opaque reference may be zero and the file itself is never stored.
- **approveMilestone:** The named client approves a current submission before reviewEnd. Approval marks the milestone Released and credits its full principal to the freelancer without calling the token, so a recipient transfer failure cannot block this settlement.
- **rejectMilestone:** The named client can reject a submission before reviewEnd while this milestone has revisions left. A nonzero reason commitment and independent rejection count are recorded, and a bounded responseEnd starts from this rejection.
- **resubmitMilestone:** The named freelancer appends the next version before responseEnd, including when the original delivery grace has already passed. It restarts review from the new submission time, preserves old versions and stays within at most revisionLimit+1 records (six maximum).
- **releaseAfterSilence:** Anyone can release a Submitted milestone at or after reviewEnd. It credits only the named freelancer and makes the milestone terminal once, rather than allowing the caller to choose who gets paid.
- **refundAfterMissedDeadline:** Anyone can refund a Ready milestone at or after graceEnd. It credits only the client and cannot refund a submitted, rejected or terminal milestone through the missed-delivery path.
- **refundAfterRejectionWindow:** Anyone can refund a Rejected milestone at or after responseEnd. A resubmission changes its state, so an old historical responseEnd can never refund a new Submitted version.
- **getSubmission:** Reads one immutable version's number, hash, opaque reference and submission time. Unknown jobs and out-of-range indexes revert instead of returning a misleading empty record.
- **getMilestone / responseWindow:** The milestone read model includes the current state, latest submission/rejection clocks, independent counts and latest reason. The response duration is immutable and shares the existing configured fundingWindow in this compatible local-only build; old response timestamps are historical unless state is Rejected.
- **terminal settlement helper:** A successful approval or timeout changes milestone state and moves exactly its principal from lockedEscrow into the rightful party's claimable balance in the same transaction. It counts terminal milestones and closes the job only when all are terminal, makes no token call or codehash check, and cannot be called as an arbitrary external payout endpoint.

Closed means all milestones are terminal, not that every beneficiary has withdrawn. Withdrawal stays a separate guarded exact-transfer operation and can fail if an issuer blocks transfers or changes runtime code; transaction rollback preserves the claim. The Phase 1 derived credit fixture remains under tests and is not part of real settlement. Disputed/Resolved remain reserved future states with no Phase 2 entrypoint; arbitration and its bounded exits are Phase 3.
