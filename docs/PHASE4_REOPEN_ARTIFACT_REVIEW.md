# Phase 4 reopen: public artifact and backup-key evidence

## Public artifact exclusion

Hero Prompt §11 requires a build check to prove that development features, time warp, and mock randomness are absent from the production build. Current evidence does not meet that requirement. `scripts/public-build-check.mjs`, `scripts/web-build.mjs`, and `apps/web/next.config.ts` all fail closed for a public target before Next compilation. Their tests prove that release is refused while production configuration is missing; refusal creates no artifact to inspect.

The local artifact check has a narrower scope. `scripts/web-trace.test.mjs` reads the completed local build's `.nft.json` traces and verifies that `infra/local/runtime` data is not packaged. It does not check for development routes or controls. The app tree still contains `/api/dev/rpc`, `/api/dev/time-warp`, and `/api/dev/randomness/*`; handlers also check the local target at runtime. A runtime 404/guard does not prove that those route modules are absent from a production bundle. The existing `phase4-public-build-denied-final.txt`, `phase5-public-build-denied-final.txt`, and `PHASE5_RELEASE_CHECKLIST.md` correctly say there is no public artifact and the exclusion claim is blocked.

No safe actual-production artifact can be produced from the supplied configuration. Missing inputs include an approved production randomness adapter and deployment configuration, production chain/RPC and contract/token policy, and the production public-origin/TLS/HSTS/CSP and rate-limit settings. No public deployment is needed to do a future build, but a production-shaped artifact must wait for approved adapter/configuration contracts. This review did not run either build wrapper or modify build configuration.

The smallest useful next proof was a separate, explicitly non-deployable artifact-test target that builds in an isolated temporary app directory. The result and its limits are recorded below. Keep the existing `public` target blocked until the real adapter and production configuration are approved.

## Backup-key helper check

The historical ignored runtime backup contains `before.json` and `private.db` but no `server-env.json`; it cannot recover its old ciphertext after the later key rotation. That limitation remains. The current `scripts/phase5-evidence-migration.mjs --before` path copies `server-env.json` into its backup, but the real historical run predates that change and cannot prove the new behavior.

Added `scripts/phase5-backup-key-preservation.test.mjs` as supplemental GREEN evidence. It provisions a fresh SQLite database and synthetic AES-GCM row in an OS temporary directory, invokes the existing helper with that temporary directory as its working directory, then reads the copied database and environment file and decrypts the row. The test prints no key material. It hashes the schema, helper, Next/build gates, and generated Prisma client before and after; it uses Prisma `db push --skip-generate` and asserts those hashes stay unchanged. The test never opens or writes the owned runtime or its historical backup.

Command: `node --test scripts/phase5-backup-key-preservation.test.mjs` — **1 passed, 0 failed**.

This demonstrates the current helper can copy a matching key beside a copied database in an isolated fixture. It does not restore the historical backup, encrypt backup files, establish protected key storage or key rotation/recovery procedures, or qualify the helper as an operational or production backup. The human F-74 backup video remains outstanding.
